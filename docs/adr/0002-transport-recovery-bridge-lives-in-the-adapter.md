# Keep the transport-recovery bridge in the adapter, not in `rithmic_gateway`

`TransportRecoveryBridge` (`rithmic_nt_connect/recovery_bridge.py`) owns listener wiring, the thread hop, single-flight, generation dedupe and bounded retry for the data and exec clients, while `rithmic_gateway.transport_recovery.TransportRecovery` keeps owning only the dial and the `TransportDown` / `TransportUp` / `RecoveryFailed` events. Folding replay and re-arm into the gateway package was rejected: the 2026-09-02 transport-recovery brief and migration plan (R4, R8) require that the gateway never owns MD replay, order-plant re-arm or capability policy, that an L3 reconnect disarms exec before reconciling, and that a ticker reset (L0–L2) must not. The clients therefore inject only what to restore (`restore(generation, attempt)`) and what to do on down / failure; the bridge never dials. Direct sessions have no transport events, so attaching there is a deliberate no-op — direct mode has no L3 recovery (tracked in `docs/STATUS.md`).

**Amended (2026-10-14).** The dial and the transport events are now the Rust gateway client's, and the adapter defines the event types itself (`rithmic_nt_connect/transport.py`) so it imports neither `rithmic_gateway` nor protobuf. The decision is unchanged: restore policy stays in the bridge, the client only reports `down` / `up` / `recovery_failed`.
